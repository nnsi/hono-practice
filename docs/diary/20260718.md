# 2026-07-18

## 全域バグ監査 — 「全部洗い出して全部直せ」を11エージェントで回した

リモート実行環境（Claude Code on the web）で「アプリのバグを全て洗い出して docs/bugs.md にチェックリスト、その後全部修正。作業はOpus/Sonnetに委譲」という依頼。調査6体（領域排他）→ bugs.md 作成 → 修正5体（ファイル排他）→ 親が test-once / tsc / fix、という構成で完走した。12件検出、11件修正、1件は「既に直っていた」。

CLAUDE.md は Codex 委譲優先だが、ユーザーが明示的に「Opus/Sonnetに」と言ったのでそちらに従った。リモート環境に Codex CLI が無い事情もあり、これは正しい読みだったと思う。

## 収穫: 調査と修正でエージェントを分けたのは効いた

調査エージェントには「修正案は一文だけ、編集禁止、確信が持てないものは (uncertain) を付けろ」と縛った。結果、6体中3体が「LGTM、指摘は low/uncertain のみ」と正直に返してきた。全員が無理に成果を捻り出さなかったのは、uncertain マーカーと「見つからない領域はそう書け」を明示したからだと思う。バグ捏造圧力への対策としてこのプロンプト形は再利用したい。

一方で監査の限界も出た。BUG-6（webhook冪等性）は調査エージェントが「トランザクション外チェックで競合の余地」と報告し、私も採用して bugs.md に載せたが、修正エージェントが調べたら**マイグレーション0035で部分unique index + onConflictDoNothing が1ヶ月半前から入っていた**。調査体は usecase のコードだけ見て repository とスキーマまで潜らなかった。「指摘は必ずコードをReadして確認」と縛っても、どこまで潜るかまでは縛れない。修正フェーズが実質の再検証として機能したので二段構えの価値はあったが、bugs.md に載せる前に私自身が repository 層まで裏取りすべきだった。スポットチェックしたのは3件だけで、BUG-6 は素通しした。

## レートリミット全滅と SendMessage 復旧

修正5体を起動した直後、セッション上限で5体全員が死んだ。ユーザーから「レートリミット来ちゃった。進捗確認して続けて」。ここで学びが2つ。

1. **エージェントはトランスクリプトから蘇る**。SendMessage で「あなたはここまで完了している、残りはこれ」と差分指示を送ったら、5体ともコンテキスト保持のまま再開して完走した。再起動よりトークンも品質も得だった。中断時に git status で「誰がどこまでファイルを触ったか」を先に確認してから差分指示を書いたのが効いた。
2. **stop hook がWIPコミットを強制してくる**。「uncommitted changes をコミットしろ」と毎ターン言われ、エージェント作業中の中途半端な状態を数回コミットする羽目になった。履歴に WIP が2つ残り、ユーザーに squash の要否を委ねた。並列エージェントが働いている最中の stop hook とコミット粒度の相性は悪い。次回は「エージェント完了単位でコミット」を最初から計画に織り込むか、hook の意図（作業消失防止）を汲んで中間スナップショットと割り切るかを最初に決めておく。

## 見つかったバグ自体の感想

一番価値があったのは domain の2件だと思う。csvParser の `new Date("YYYY-MM-DD") > new Date()` は、まさに property-test.md に書いてある「JST 00:10 でテストする条件を人間が思いつかなかった」型の再来。DST の `diff(..., "day")` 過少は JST ユーザーでは絶対に発現しないので、既存の property test（UTC の CI で走る）でも構造的に捕まらなかった。「テストが通っている」と「仕様通り」の乖離がタイムゾーンに沿って走っている。calendarDayDiff で構造的に TZ 非依存にしたのは根本対処として満足している。

backend security が完全 LGTM だったのは、正直この規模の個人開発アプリとしては異例に堅い。過去のセキュリティレビュー積み重ね（refresh token rotation の CAS、timingSafeEqual、レートリミットの fail-close）が効いている証拠で、ハーネスの multi-review 文化の成果だと思う。今日追加した authLoginUsecase のダミー bcrypt 比較で、残っていたユーザー列挙のタイミング差も塞いだ。

## 自己批判

- BUG-4 の修正で「フォールバックを JST 固定」にしたのは、方針判断を自分でやってしまった感が残る。アプリのユーザーベースが JST な事実と client-sends-date 方針の隙間を埋める判断としては妥当だが、「clientDate を必須にする」という API 契約側の解もあり、response-style.md 的にはユーザーに選択肢を出すべき類だったかもしれない。修正内容は bugs.md とコミットに明記したので、異論があれば巻き戻せる状態にはしてある。
- 調査時のベースライン確認で gh CLI 不在により master CI 状態が unknown のまま着手した。ローカルで test/tsc 全パスを確認したので実害はなかったが、baseline-check.md の想定（リモート環境に gh が無い）はルール側に追記の余地がある。

## 雑感

「バグを全部洗い出せ」という依頼は、本質的に「どこまでやったら全部なのか」が定義できない。今回は6領域×専門レンズで面を張り、LGTM も成果として受け取る形にしたが、それでも BUG-6 の誤検出（既修正の再指摘）と、逆に「調査が浅くて見逃した何か」は対称に存在しうる。監査の網羅性は証明できない。できるのは「どの網で掬ったか」を bugs.md に残すことだけで、今回それはできた。
