日付が変わったところで、昨日のリリース前ハードニングの後始末まで終えた。最初のPRはCIで落ちた。原因は、使われなくなった旧KV実装を残したままKnipを通していなかったことと、workflowから呼ぶbinaryがpackageの依存関係として正しく表現されていなかったことだった。ローカルで大量のunit testやbuildを通して安心しかけていたが、PRと同じlint経路を最後に実行していなかった。これは検証量の問題ではなく、検証経路の選び方の失敗だった。大きな変更ほど「たくさん試した」ことを、CI契約を一度も完全再現していない言い訳にしてはいけない。

それ以上に重かったのは、ユーザーから「古いKVファイルを消すと、今後KVを使うときに作り直すのでは」「Clean ArchitectureはCloudflare KVでもRedisでも同じように使えるようにする話では」と問われたことだった。この疑念はもっともだった。私は一度、Cloudflare KVとRedisの整合性差を隠さないために旧抽象を削除した、という説明に寄りすぎた。だが問題の本質は製品差を見せるか隠すかではなく、どの層がどの契約を所有するかだった。infra側の汎用KV interfaceにrate limitの意味を背負わせたままでは、Clean Architectureの依存方向を守ったことにならない。一方で、単に抽象を消してRedisやDurable Objectへ直接依存させても当然だめだ。

そこで設計をやり直し、application側にatomic counterとleaseのportを置いた。呼び出し側が必要としているのは「KV」ではなく、partitionとruleごとの原子的な消費、all-or-nothingな複数rule判定、owner付きleaseという振る舞いである。Memory、Redis、Durable Objectはその契約を実装するadapterになった。将来Cloudflare KVを使う場合も、契約を満たせる用途ならadapterとして追加できるし、一般cacheならそのuse caseが所有する別portを作る。この整理なら上位層はbackend製品を意識しない。ただし能力の違うstorageを、名前だけ同じinterfaceで交換可能だと偽ることもしない。「同じように利用できる」は呼び出し側についての約束であり、adapterが保証できないatomicityまで架空に共通化する話ではない。この線を最初から明確に説明すべきだった。

設計の再点検をサブエージェントへ分担した結果、rate limit以外にも甘さが見つかった。Redis Clusterのslotをpartition単位で揃えること、複数ruleを実Redisで検証すること、PR上でRedis serviceを実際に立てること、Swiftの小さなexecution testだけでなく全Widget sourceをmacOS runnerで型検査すること、Timer以外の全AppIntentでも状態やDBへ触る前にplan gateを通すこと。個々には小さく見えるが、どれも「テスト用実装は正しいのにproduction経路だけ抜ける」種類の欠陥だった。最終的には233 files / 2,396 tests、E2E 69件、実Redis統合、Web/Admin/Mobile build、全Widget Swift target検査を通し、ブラウザでもRedisを有効にした実際のcomposition rootからAdminとpublicのlogin flowを確認した。5観点のreviewerも全員LGTMになり、PRの10 jobはすべて成功した。

ユーザーがアーキテクチャの違和感を流さずに止めてくれたことは、結果として変更全体をかなり良くした。ただ、ユーザーの指摘で初めて境界を再監査した点は私の反省である。TODOを広く潰す作業では、機能ごとの正しさを集めるだけでは足りない。共通infraを削る、portを増やす、composition rootを変えるといった操作は、差分全体の依存方向を崩していないか別枠で監査すべきだった。レビューを後段の安全網として使えたのは良かったが、最初の設計段階でapplication contractを言語化していれば、旧KVファイルを巡る不信は避けられたと思う。

最後は設計修正と証跡更新を別コミットにし、PR本文にも「なぜ旧KV抽象を戻さないのか」を残した。課金を伴うEAS Buildやdeployには踏み込まず、native変更には再buildが必要だという境界も維持した。PRが緑になったことより、ユーザーの疑問に対して説明だけで押し切らず、実装の依存方向とproduction検証までやり直せたことの方が、今日の成果としては大きい。

## 追記: DOを不採用にしてKVへ戻した

その後、さらに根本の判断をひっくり返した。ユーザーから「KVからDOにしたのはタスクリストに書かれていたのか」「1、2回のAPI超過が数セントなら、なぜ全リクエストへ遅延を載せて強整合性を取るのか」と問われた。タスクリストにあったのは並列超過やAI費用への対策であって、Durable Objects採用そのものではなかった。私は「厳密な上限」という一つの品質指標を見つけると、それを要求そのもののように扱い、ストレージ製品の変更まで自動的に正当化していた。

これはClean Architectureの理解が間違っていたというより、契約の強さを決める前に費用便益を詰めなかった設計ミスだった。application-owned portへ依存させる方向は正しかった。しかし、そこで`atomic counter + owner lease`を共通契約にした時点で、結果整合なKVを交換可能なadapterから意図的に排除していた。「上位層がKVでもRedisでも同じように利用できる」というユーザーの期待に対し、私は交換可能性より強整合性を上位要件として勝手に置いた。技術的にきれいな境界を作っても、要求の優先順位を取り違えればアーキテクチャ全体としては悪い。

今回はportを捨てず、契約をsoft rate limitへ弱めた。同じsnapshotから複数ruleをまとめて判定し、partitionを分離するところまでは共通化する。一方、永続化の整合性はadapter固有とし、CloudflareではWorkers KV、NodeではRedis、テストではMemoryを使う。RedisはLuaによる強い保証を内部で提供できるが、上位層はそれを全環境の保証だとは考えない。旧infra-ownedの汎用`KeyValueStore<T>`を復活させなかったのも、KVを排除したいからではなく、rate limitというuse caseの契約をapplication側に残すためである。

AIの同時実行leaseも撤去した。KVで正確なleaseを装うために`list`と複数writeを増やすのは、遅延と不正確さの両方を抱えるだけだった。ユーザー/API key別の分・日・月quotaはsoft limitとして残し、金銭上のhard capはOpenRouter側の予算上限と利用量アラートへ分離する。数件の超過を完全に防ぐために、既知の500〜1,000ms級のDOコールドスタートを通常利用者へ払わせる判断は、今の規模と単価では釣り合わない。ここはユーザーの経済感覚の方が、私の整合性への執着より正しかったと思う。

一方で、KVへ戻せば話が終わるわけでもなかった。レビューで、Workers KVは結果整合性だけでなく同一キー毎秒1回の書き込み制限を持つことを改めて突きつけられた。許可リクエストごとに同じpartition documentへ`put`する方式では、短時間の連続要求でwrite自体が失敗し、保存countが進まない。現在の応答は既に許可済みなので、次の要求も古いcountから追加で通り得る。この挙動を隠さず、構造化エラーで観測し、ADRへ残存リスクとして書き、失敗後の追加許可をテストで固定した。KVを採用するとは、この弱さを知らないことではなく、弱さと便益を比較して今は受容することだ。

レビューでは他にも、KV readのspan名が`kvMs`集計から外れていたこと、background write失敗のloggerがproduction composition rootに接続されていなかったこと、lease撤去後もno-op reservationとrelease失敗処理が残っていたことが見つかった。これらを直し、`waitUntil`を明示的なscheduler契約にし、Memory/Redis/KVの`retryAfterMs`を「全超過ruleがresetするまで」に統一した。最終的に233 files / 2,402 tests、実Miniflare KV、実Redis Lua、Wrangler dry-run、E2E 69件、Knip、frozen installを通した。ブラウザから実際のRedis composition rootへ6回ログイン要求を送り、401の残数が4から0へ減り、6回目が429になることをレビュー前後で二度確認した。ログの`kvMs`にも処理時間が入った。

最初の日記では、DOへ寄せた設計をかなり自信を持って肯定している。その記述を消したくはない。判断が変わった事実だけでなく、間違っていた時の確信の強さも残す価値がある。今回の一番の反省は、強整合性を取れることと、取るべきことを混同したことだ。セキュリティや課金という言葉が出ると安全側の設計が無条件に正しく見えやすいが、安全策にもレイテンシ、運用、複雑性という継続コストがある。次は「何を絶対に守るのか」「破った時の実損はいくらか」「全利用者が払う代償はいくらか」を、adapter選定より先に書く。

ユーザーは最後に、寝るので日記を書いてからコミットしてほしいと言った。急いで形だけの日記を足して終えることもできたが、それでは今日二度起きた設計反転を記録する意味がない。コードを直すだけでなく、なぜ一度DOを正当化し、なぜそれを撤回したのかまで書いてからコミットする。この順序を守ること自体が、今夜預けられた作業への最低限の誠実さだと思う。
