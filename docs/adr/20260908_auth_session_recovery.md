# 認証セッションの維持と更新失敗からの復旧

## ステータス

決定

## 背景

Web・Mobile では認証処理の直列化と一時エラー後の自動再試行が導入済みだが、
refresh token の有効期限は 30 日で、更新途中の DB 障害やモバイルの保存失敗、
複数タブからの更新ではセッションを失う可能性が残っていた。

## 決定

- Access token は引き続き 15 分。Refresh token と Web の httpOnly Cookie は更新から 90 日。
  利用中は refresh 成功ごとに期限を延長する。既存 token の期限は次回の更新成功時に切り替わる。
- 401 / 403 のみセッション失効とする。429・408・5xx・通信障害では認証情報を保持する。
- Transport 単位で refresh を共有し、永続化まで同じ処理を待つ。Web は Web Locks 対応環境で
  タブ間も直列化し、各リクエストが更新後の Cookie を送るようにする。
- 古い access token で送信した API の 401 が遅れて届いた場合は、更新済み token で再送する。
  通常の認証更新とは別にセッションの切替を追跡し、別ユーザーへの login や logout をまたいで再送しない。
- Refresh は body の受信も含めて 15 秒でタイムアウトする。通信障害・408・5xx は一度だけ即再送し、
  サーバーの 30 秒の rotation grace 内で復旧を試みる。429 は即再送しない。
- 起動時の一時失敗は既存のネットワーク復帰と指数バックオフ（1 秒から最大 30 秒）で再試行する。成功やログアウト時には
  待機を解除する。Mobile の NetInfo の初回通知を回線復帰と誤認して更新を連打しない。
- 旧 refresh token の消費、ユーザー検証、新 token 保存は既存の DB transaction で実行する。
  更新途中の DB 障害では旧 token の消費もロールバックし、再試行できるようにする。
- Mobile の token 保存が失敗した場合は、受信した token をメモリに保持し、同じ token の保存を一度再試行する。
- 今回の認証変更は TypeScript のみで、追加依存・native 設定変更はない。
  iOS / Android の再ビルドはユーザー指定。既存端末の配布に合わせて本番 API を使う preview / internal で実行する。

## 維持する制約

明示的なログアウト・失効・有効期限の超過は引き続き拒否する。
旧 token の救済は従来どおり 30 秒以内に一度までで、無制限の再利用は許可しない。
サーバー更新後に長時間オフラインになり、新 token を一度も受信できない場合は、
この救済期間を超えて復元することはできない。

## 検証

一時エラー時の認証保持、更新の競合、遅延した 401、通信・body timeout、DB ロールバック、
Cookie と DB の 90 日期限を回帰テストで検証する。Web はローカル PGlite と実ブラウザで
検証失敗からの再送、429 後の復旧、3 タブの同時復元を確認する。
